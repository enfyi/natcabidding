# Bidding backup installation

Enable the Supabase Cron integration (pg_cron), then run `database/bidding_backups.sql` in the target project's SQL editor after the administrator helpers in `bid_line_import.sql`. The installation is transactional and intended to run once. It creates an admin-only schedule and snapshot history, and a named Cron job checked every minute.

In Bidding Setup → Backups, choose inclusive start/end dates, a daily time window in Pacific time, and an interval in minutes. Save the schedule with automatic backups enabled. The interval restarts at the beginning of each day's window. Cron runs on minute boundaries; after downtime it captures the latest due interval, without generating historical snapshots. The schedule automatically stops outside its dates and time window. Disable and save to stop it early. Avoid overnight windows; choose 00:00–23:59 for a full day.

Back Up Now immediately runs an authenticated database operation independent of the automatic schedule. Completion is displayed only after the snapshot is saved. Administrators can download the latest snapshot as JSON. Snapshots use one consistent query across all public application tables, excluding backup history and scheduling tables. They include personal bidding data; keep downloaded copies private.

These are application-data snapshots stored in the same database. They do not include Auth accounts, Storage files, schema definitions, or a one-click restore facility. Keep independent off-site database backups as well. Leave auto-delete days blank to keep all backups, or enter a positive whole number of days. Cleanup deletes snapshots strictly older than that age, always preserving the most recent snapshot (creation time, then ID for ties). It runs every minute even with automatic capture disabled or outside the date/time window. Downloaded copies are unaffected. For an already installed backup system, run `database/bidding_backup_retention.sql` to add retention support; monitor database size and Cron job run failures in Supabase. Test the installation on a development database before production.

Verification after installation: run Back Up Now as an admin; confirm a new row and download. Confirm a non-admin cannot read snapshots or call backup_bidding_now. Configure a short schedule and confirm a scheduled row appears with the page closed. Inspect cron.job_run_details for failures. Run `scripts/test-bidding-backup-retention.sql` in a development database to verify retention edge cases (the test rolls back all changes). Live database verification is required before deployment.
